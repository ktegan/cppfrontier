# Language Rules

The Cpp2 documentation (`../cppfront/docs/cpp2/*.md`, upstream's `docs/cpp2`)
is the base language. This file states the rules cppfrontier follows where
those documents are silent or allow more than one reading. Each rule applies
the same way to every input; [README.md](../README.md#design-principles) gives
the criteria for choosing one. A name in parentheses, such as
`chained-assignment`, is the translator's diagnostic. "Left to the Cpp1
compiler" means the translator emits the code as written and the Cpp1
compiler reports the error. Rules that differ from upstream cppfront are also
listed in [UPSTREAM_DIFFERENCES.md](UPSTREAM_DIFFERENCES.md), and opt-in
changes to these rules in [EXPERIMENTS.md](EXPERIMENTS.md).

## Declarations

- **Names** are contextual: one set of predicates decides where a word is a
  name, in declarations, parameters, template parameters, members, locals,
  labels and names generated by metafunctions. `__identifier__` escapes a
  name, and upstream's Cpp1 escape set (`class`, `default`, ...) lowers to
  `cpp2_<name>`. A name that is reserved in Cpp1 and outside that set, such
  as `namespace`, is rejected, since it has no valid Cpp1 spelling.
  Structural words (`this`, `that`, statement keywords) are never names.
- **Reserved names.** Names beginning with `__cpp2_` belong to the translator
  (`reserved-name`). The runtime support names (`unchecked_*`, `finally`,
  `cpp1_ref`, `cpp1_rvalue_ref`) cannot be declared
  (`reserved-support-name`): the translator qualifies them unconditionally,
  so a user declaration would give one spelling two meanings.
- **Fundamental aliases.** Exactly the aliases of common.md "Fundamental data
  types" are keywords, `uint` included; `f32` and `f64` are ordinary names.
- **Anonymous objects.** An object can have an anonymous name or an
  anonymous type, not both: `_ := f();` and `_: _ = f();` are
  `anonymous-object` in every scope. `_ := f()` is one character from
  `_ = f()`, which destroys the result at once, so a guard written one way
  would silently unlock with the other. `_: T = f();` declares an unnamed
  object; an unnamed data member is copied, moved, compared and hashed by
  the members metafunctions and `operator=` generate, as a named one is.
- **Own initializer.** An object, local or statement parameter whose
  initializer names itself, `g: int = g + 1;`, is `own-initializer` in every
  scope.
- **Namespace-scope objects** need a declared type unless they are `==`
  constants, since a deduced type cannot be declared before its definition,
  and their initializer is an expression: `x: int = { return 1; }` is
  rejected. Declaration order does not matter: a `==` constant or object
  named by a signature or member initializer earlier in its namespace is
  declared before that use, with the later constants and constexpr functions
  it names. It stays in place when something it names, or a Cpp1 line, comes
  between the two.
- **Object aliases** are `constexpr` in a function, `inline constexpr` at
  namespace scope and `static constexpr` members at type scope.
- **Templates.** Metafunctions come before template parameters, and a
  trailing comma in `<...>` is dropped, as in every list. A template
  parameter declared twice, and a pack that is not the last parameter of a
  template other than a function, are diagnosed. A `requires` clause follows
  a function's declarator and precedes a type, object or alias. A template
  parameter that shadows an enclosing one, a fold or `sizeof...` over a
  non-pack, and an unexpanded pack are left to the Cpp1 compiler.
- **Conversion functions** `operator T: ...` are `conversion-function`, which
  suggests a named function or `operator=: (implicit out this, ...)`.
- **Left to the Cpp1 compiler:** a parameter or local declared twice in one
  scope, `t: _ = ();`, and a template `main`.
- **Beyond the documentation**, the features that upstream supports and its
  documentation omits, listed in ARCHITECTURE.md
  [Cpp2 Coverage](ARCHITECTURE.md#cpp2-coverage), are part of the language.

## Types

- **`_`** lowers to Cpp1 `auto`, so it can be a declared type, what `*` and
  `const` qualify in one (`*_`, `* const _ is C`, lowered as `C auto*`), or a
  function type's return type. It is rejected in a template argument, a type
  operator's operand and a function type's parameter (`nested-wildcard`). An
  operator constraint `_ is C` applies only to a whole `_`.
- **Every type position is checked alike**: a declared type, an alias's
  value and a typed value `:T = v`.
- **No Cpp1 references.** A written `T&` or `T&&` in a type, a type
  alias's value and `decltype(e)&` included, is `cpp1-reference-type`:
  passing styles pass by reference, and `cpp1_ref<T>` names a Cpp1
  reference.
- **Template arguments** use Cpp2 type syntax: a Cpp1 declarator such as
  `T const` or `int*` is `cpp1-declarator-in-template-argument`. Since `Foo*`
  is a dereference in Cpp2 and `*Foo` the pointer type, a trailing `*` is
  `postfix-star-in-template-argument`. In a template argument `|` and `&` are
  Cpp1 operators, as in `std::bitset<A | B>`. C arrays such as
  `std::unique_ptr<int[]>` pass through, since Cpp2 has no other way to write
  them.
- **`sizeof`, `alignof` and `typeid`** take a Cpp2 type-id when their
  argument begins with `*` or `const`, and check it as a template argument:
  `sizeof(*int)` is `sizeof(int*)`, `alignof(const T)` is
  `alignof(T const)`, and `sizeof(const int&)` is
  `cpp1-declarator-in-template-argument`. A type-id that names no type,
  `sizeof(const)` or `alignof(* const _)`, is `deduced-type-operand`. Any
  other argument is an expression or a type name.
- **Dependent names.** `type T::x` marks a type wherever a type-id may
  appear, and an alias of a dependent type carries the dependence. In a type
  position, a qualified name whose first component is an enclosing template
  type parameter, or whose scope has template arguments that mention one, is
  dependent and lowers with `typename` (and `template` before a later
  templated component). Template arguments are not marked, since Cpp2 does
  not say whether `T::x` there is a type or a value; the `type` marker
  decides.
- **Function types.** A function pointer parameter takes its passing style
  as any type does (`in` and `copy` pass it by value), a function type may
  return a function pointer, and named returns in a function type are
  rejected (`function-type-named-returns`).
- **Constraints.** For `_ is C<...>`, when `C` is declared in this
  translation unit, the translator checks what needs no C++ semantics: `C` is
  a concept, its first parameter takes a type, and it accepts the written
  arguments plus the constrained type (`constraint-not-concept`,
  `constraint-not-type-concept`, `constraint-argument-count`). Only a name
  can be a concept, so `_ is int`, `_ is *T` and `_ is decltype(e)` are
  `constraint-not-concept` wherever the name is declared. Whether a type
  satisfies a concept, and constraints on names declared elsewhere, are left
  to the Cpp1 compiler.

## Functions and parameters

- **`in_ref`** is its own passing style and lowers to `T const&`.
  `forward_ref` is a return form only and is rejected for a parameter.
- **Typed `out` parameters** lower to `cpp2::impl::out<T>`, which constructs
  once: a direct assignment is `.construct(rhs)`, other uses read through
  `.value()`, and an `out x` argument is `cpp2::impl::out(&x)`. An omitted or
  `_` type is a deduced `auto x_` with the prolog
  `auto x = cpp2::impl::out(x_);`.
- **Typed `forward` parameters** add the constraint
  `std::is_convertible_v<CPP2_TYPEOF(x), std::add_const_t<T>&>`, combined with
  any written `requires` clause.
- **Deduced `move` parameters** take only rvalues, as every `move` parameter
  does: one whose `&&` is a forwarding reference (`x: _`, a typed pack
  `xs...: X`, or `x: T` with `T` a type parameter of the function) adds the
  constraint `!std::is_lvalue_reference_v<decltype(x)>`, so an lvalue
  argument is rejected rather than moved from at the parameter's last use.
- **Constrained parameters.** `x: _ is C` lowers to `C auto` for `in`, `copy`
  and `inout`, so overloads are ordered by subsumption.
- **Deduced defaults.** `y := 2` lowers to a template parameter whose default
  is the default argument's type, so the argument can be omitted.
- **Default order.** A parameter with a default followed by one without is
  left to the Cpp1 compiler, for function and template parameters alike.
- **Requires-expression parameters** use Cpp2 parameter syntax,
  `requires (inout a: T) { a += a; }`.
- **Function expressions.** After an expression body,
  `:(x) = f(x);(a)` invokes the function when the parenthesized text is an
  expression list; otherwise the `;` ends the statement.
- **Virtual functions** may have an expression body. One that deduces its
  return type is `virtual-deduced-return`, since Cpp1 forbids it, and one
  with named returns is `virtual-named-returns`: each class would declare
  its own result struct, an invalid covariant return type in Cpp1, and a
  single named return is rejected alike, so the rule does not depend on the
  count.
  `override`, `final` and `@interface` functions are virtual.
- **Contracts** are checked by the body, so a function without one (a pure
  virtual or `@interface` function, a defaulted `operator==`) cannot have
  them (`contract-without-body`). A constructor's preconditions are checked
  on entry, before its member initializers evaluate anything, so
  `pre(!n.empty())` reads the argument that `name = n;` then moves; an
  assignment checks them before it assigns the members.
- **Comparison operators**, member or not, have their return type checked:
  `==` to `>=` declare `-> bool`, and `<=>` is deduced or a `std::` ordering
  category (`comparison-return-type`).
- **`==` functions** with side effects are left to the Cpp1 constexpr rules.
- **`that$` in a copy constructor** (`operator=: (out this, that)`) is
  `copy-captures-that`, since copying `that` calls the constructor again.
  Its members can be captured, `that.n$`.
- **Pack captures.** A capture whose expression mentions an unexpanded
  parameter pack, `xs$...` or `(xs + 1)$...`, captures each element: it is
  the init-capture pack `..._0 = xs`, in a function expression or a
  postcondition. `sizeof...(xs)$` is one value.

## Returns

- **Return forms.** `-> forward_ref _` lowers to `auto&&`. A typed
  `-> forward T` lowers to `T&`, or `T const&` for an `in this` receiver.
- **`return;`** is allowed in a function declared `-> void`.
- **What a return refers into** is the object named by its leading name,
  followed through member accesses, subscripts, calls, postfix operators and
  parentheses, up to a postfix `*` dereference. So `return s.x;` refers into
  `s`, and `return it*.second*;` does not refer into `it`.
- **Forwarding returns.** A reference return may not refer into an object the
  function owns: a local or a `copy` or `move` parameter. A `-> forward T` or
  `-> forward_ref _` function always returns a reference, so such a return is
  rejected there, and so is one into an `in` parameter, which may be passed by
  value. A `-> forward _` function and an expression body deduce a value or a
  reference from the returned expression's `decltype` (functions.md), so the
  generated Cpp1 holds `static_assert(!std::is_reference_v<decltype(expr)>)`
  for an owned object: `return i;` and `(copy x: int) = x` return a copy,
  and `(move s: std::string) = s`, a `std::string&&`, is rejected by the Cpp1
  compiler with the translator's message. An `in` parameter is the caller's
  object, or a copy that `decltype` returns by value, so `(x) = x` is
  accepted in every function, named or not.

## Expressions

- **`(x)` is grouping** everywhere, including a `for` range; a list needs two
  or more elements.
- **No comma operator.** A list `(a, b)` is never the Cpp1 comma operator
  (common.md "Lists and commas"): as an operand, argument, condition or index
  it is `comma-operator`, and inside a list it is a nested initializer. A
  sequence in one expression is a function expression, as in the fold
  `((:(_) = f(x$))(Is), ...)`.
- **Assignment is a statement**, never a value: `a = b = 3`, `x := a = 3`,
  `x := (b = 3)` and `g(a = 3)` are `chained-assignment`, and an `if`,
  `while` or `do` condition is never an assignment
  (`assignment-condition`). Parentheses do not use the value, so `(a += 2);`
  and `next (i += 1)` are statements.
- **`>=` and `>>=` after `<`** are operators, never the close of a template
  argument list followed by `=`, so `f(a < b, c >= d)` is two comparisons and
  `std::is_same_v<int, int>>=0` is rejected; write `> =` or parenthesize.
  Splitting them would make `a < b, c >= d` a template list or need
  whitespace-sensitive parsing, which functions.md rules out.
- **Postfix `*`, `&` and `~`.** After an operand, `*` and `&` are binary
  when the next token begins an operand (a name, literal, `(`, `::`, `!`, or
  the `:` of a typed value or function expression)
  and postfix otherwise, whatever the spacing, so `p* - 1` dereferences and
  `a * (-1)` multiplies. `p*()` calls `p*`. `~` after an operand is always
  postfix. Spacing never changes the meaning, but spacing that suggests the
  other one is `misleading-postfix-spacing`: a postfix `*` or `&` with
  whitespace before it, followed by a token Cpp1 reads as a prefix operator
  (`+ - * & ~ ++ --`), as in `a * -1` (`(a*) - 1`), `a * *p` (`(a*) * p`)
  or `x & -x`. Write `a * (-1)` for the binary operator, or `a* - 1` for the
  postfix one; `a*-1`, `p* - -1` and `a *= -1` are unaffected. Before
  `* & ~ ++ --`, where `a * (*p)` is still invalid Cpp2, the binary operator
  takes the right operand written with postfix operators, `a * p*`.
- **Folds over `*` and `&`.** `...` does not begin an operand, so a `*` or
  `&` before it is postfix: `f(xs*...)` and `(xs* + ...)` dereference each
  element, and `(xs * ...)` and `(1 * ... * xs)` are
  `misleading-postfix-spacing`. A fold over `*` or `&` is a left fold,
  `(... * xs)`; with an initial value, fold the compound assignment,
  `(r *= ... *= xs)`.
- **Arithmetic on an address.** `x&` is a pointer, so `x& + 1`, `1 + x&`,
  `x&[i]`, `x&++` and the parenthesized `(x&) - 1` are `pointer-arithmetic`,
  as on a pointer object.
- **A fundamental type is not an operand.** `i32`, `int`, `double` and the
  other fundamental type names are types, so as an operand of a binary or
  prefix operator they are `type-as-operand`: `v is int | double` tests
  `is int` and then uses `double` as a value (`type-after-is`, suggesting
  `v is int || v is double`). Template arguments, `sizeof(int)`, `int(3)`
  and the type of a typed value are unaffected.
- **Values after `is`.** A parenthesized operand, a literal (`true`, `false`
  and `nullptr` among them) and an operand beginning with `-`, `+` or `!` are
  values; anything else is a type-id, so a variable is parenthesized,
  `x is (y)`. The value is one prefix expression, like the operands of
  binary operators, so `x is 1 + 1` is `(x is 1) + 1` and `x is 1 && y is 2`
  is two tests. Upstream takes the rest of the expression as the value.
- **Concept queries.** `x is C` with a concept `C` declared in this
  translation unit tests the type of `x`: `x is C<A>` is
  `C<CPP2_TYPEOF(x), A>`, without evaluating `x`. Any other name is a type or
  a template, `cpp2::impl::is<C>(x)`, so a concept declared in Cpp1, such as
  `std::integral`, does not compile there; constrain a parameter
  (`x: _ is std::integral`) instead.
- **Types on the left of `is`.** A subject that is visibly a type (a
  template type parameter in scope, a fundamental type, or a type this
  translation unit declares or an alias of one, plainly or qualified) is a
  compile-time query on the type: `T is X` is whether `x is X` is
  statically true for a value `x` of type `T`, so it matches the same type,
  a base (`D is B`), a template (`T is std::vector`) and a concept declared
  here (`C<T>`), and is false where `x is X` would test at run time, as for
  unrelated polymorphic types. It lowers to the constant expression
  `std::is_same_v<decltype(cpp2::impl::is<X>(std::declval<T const&>())), std::true_type>`.
  An `inspect` on such a subject tests each alternative the same way. A value
  or predicate after `is`, as in `T is 0` or `is (0) = ...`, is
  `type-subject-value`. Any other subject is a value.
- **`inspect` result type.** Each alternative's value converts to the
  result type, as `:T = value` does (expressions.md), so `-> _`,
  `-> *const _` and `-> void` are `invalid-inspect`, and a list value
  initializes it: `is 1 = (a, b);` is `T{a, b}` and `is _ = ();` is `T{}`.
  `(x)` is grouping, as everywhere.
- **Unreachable alternatives.** Alternatives are tested in order, so one
  after an unguarded `is _` can never be chosen and is
  `unreachable-alternative`.
- **Character literals** hold exactly one character or escape sequence, so
  `'ab'`, `'\\n'` and `''` are errors; Cpp1 gives a multi-character literal
  an implementation-defined `int` value. An unprefixed or `u8` literal holds
  one UTF-8 code unit and a `u` literal one UTF-16 code unit, so `'é'`,
  `u8'é'` and `u'😀'` are errors too; `u'é'`, `U'😀'` and `L'é'` are not. Upstream rejects them, and also rejects octal escapes
  such as `'\101'`, which are accepted here.
- **`not`.** `not` followed by whitespace is the operator `!`, so `not b` is
  `!b`. Otherwise `not` is an ordinary name: `not(b)` calls a function `not`
  and `not: int = 1` declares one. Upstream lexes it this way; its
  documentation does not mention it.
- **Qualified UFCS.** When `N::f` resolves to a function with a `this`
  parameter of a type this translation unit declares (`N` may be an alias
  of one), `x.N::f(args)` is the member call `x.N::f(args)`, a non-virtual
  call of that class's function, as `this.Base::f()` in an override.
  Otherwise, as for a namespace or a static function, it is the free call
  `N::f(x, args)` (`vec.std::ranges::sort(...)` in the docs).
- **Casts.** `unchecked_cast` is the one spelling for every type-unsafe cast:
  it reinterprets when no `static_cast` exists (expressions.md "Casts").
  `reinterpret_cast`, `const_cast`, prefix `*` and the other Cpp1-only forms
  are rejected.
- **Interpolation.** An interpolation `(...)$` ends at the `)` that matches
  its `(`, so `(f()$)$` captures `f()`. A `)$` with no matching `(` is an
  error; the adjacent literals `")" "$"` write it literally. A capture in an
  interpolation, as outside one, belongs to a function expression or a
  postcondition (its condition or message), and elsewhere is
  `unsupported-capture`. A `$` capture appears at most once in a
  postfix expression, so `x$.show$()` is an error.
  An empty interpolation, `()$` or `( )$`, is `empty-interpolation`.
  An interpolation is a `std::string`, so a prefixed literal (`u8`, `u`,
  `U`, `L`) cannot hold one: `u8"(x)$"` and `$u8R"((x)$)"` are errors.

## Statements

- **`throw;`** rethrows.
- **`for (x) do`** iterates `x`, since `(x)` is grouping, so `for (1) do` is
  not a range. A one-element range is `std::views::single(x)`.
- **A `next` clause is one expression**: `next (a += 1, b++)` is
  `next-clause-list`.
- **Jumps.** A labeled `break` or `continue` names an enclosing loop
  (`unknown-loop-label`). A bare `break` or `continue` outside every loop is
  left to the Cpp1 compiler.

## Moves and last use

functions.md defines a definite last use. These rules settle the cases it
leaves open.

- **Not a use:** a mention in a compile-time context (`sizeof`, `sizeof...`,
  `alignof`, `decltype`, `noexcept`, a requires-expression, a template
  argument) is never moved. `typeid` is a use: its operand is evaluated when
  it is polymorphic, which the translator cannot tell.
- **Never moved:** an assignment target; a mention in an `assert`, so that
  whether `g(x)` moves does not depend on contract checking; and a name
  beginning with `guard`, which is neither moved nor forwarded, `forward`
  parameters included.
- **Storage.** A `static` local outlives the call, so no mention of it is a
  definite last use. A local, or a `copy` or `move` parameter, is moved,
  `cpp2::move(x)`, only when its declared type is visibly an object type: a
  fundamental type, a pointer, or a type this translation unit declares (or
  an alias of one), named plainly or qualified (`N::X`, `X::Inner`). Any
  other declared type may be a Cpp1 reference (`std::vector<T>::reference`,
  `cpp1_ref<T>`, a `decltype`, a template type parameter or a type depending
  on one, a member of a specialization such as `Box<int>::Inner`, or a Cpp1
  alias the translator cannot see, also through a using-declaration), so the name is forwarded, `CPP2_FORWARD(x)`, which moves an object
  and leaves a reference alone. A deduced type (`x := v[0]`) and a deferred
  local, which `deferred_init` holds by value, are objects. A template type
  parameter may be given explicitly as a reference, as in
  `f<cpp1_ref<std::string>>(s)` or `W<cpp1_ref<int>>`, so `copy x: T` is
  forwarded, which moves a deduced argument.
- **One mention per statement.** A statement that mentions a name twice, as
  in `f(x, x)`, is not its definite last use, except that the values of an
  inspect's alternatives are exclusive paths: in
  `inspect v -> T { is 1 = take(x); is _ = x; }` each mention is a last use.
  A mention in the subject, a pattern or a guard is evaluated with them.
- **Leaving the scope.** A `return`, `throw`, `break` or `continue` leaves the
  name's scope, so the last mention before it is a definite last use
  (`if b { g(x); return; }`), unless it is inside a loop the name outlives. A
  `catch` handler's last mention is a last use; a mention in the `try` body
  is not when a handler may mention the name after it.
- **Postconditions.** A parameter that a postcondition mentions is moved only
  by a `return`, which runs the postconditions first.
- **Reference parameters.** A definite last use is moved even as an argument
  to a non-const lvalue reference parameter, so `std::exchange(x, 0)` as a
  last use does not compile, and a later mention (`_ = x;`) keeps the call
  from being the last use.
- **Packs.** A `move` or `forward` pack is moved or forwarded at its definite
  last use, in its own expansion: `g(CPP2_FORWARD(xs)...)`.
- **Returned names.** Where the return type is deduced by `decltype`, a
  returned name is not moved, since `cpp2::move(x)` would return a reference;
  elsewhere `return x;` is left to Cpp1's implicit move.
- **`move that`.** In a `move that` function, `that` is an ordinary `move`
  parameter: every mention, including `that.m`, is a use, and only the
  definite last use moves (`cpp2::move(that).m`). The generated memberwise
  default moves each member, and `(move that.m)` moves one explicitly. The
  move variant generated from a copy function follows the same rule.
- **Member copies.** The warning `member-copied-not-moved` names a member
  read `p.m` of a `move` parameter that copies the member whole: an
  initializer, an `=` source or a returned value. A call argument, including
  an operator's operand as in `p.a + p.b`, is not warned about, since the
  callee may not copy.

## Initialization

- **Deferred locals.** An uninitialized typed local lowers to
  `cpp2::impl::deferred_init<T>`, which constructs once. Its first direct
  assignment of a list constructs from the prvalue
  `std::type_identity_t<T>{elements}` with `.construct_from`; of an
  arithmetic literal, with `.construct(std::type_identity_t<T>{value})`; and
  otherwise with `.construct(value)`. List initialization keeps narrowing
  diagnostics. Later reads use `.value()` and later assignments assign to
  `.value()`. `decltype(x)` of a deferred local or an `out` parameter is its
  declared type `T` wherever `x` finds it, in a type and an expression alike,
  in a statement or `for` parameter, a local alias, the signature, `requires`
  clause and body of a function expression, and as the scope of
  `decltype(x)::member`;
  an `out` parameter's also in its function's later parameters, return type
  and `requires` clause.
- **Deferred references.** A local without an initializer whose type is
  visibly a reference, `cpp1_ref<T>`, `cpp1_rvalue_ref<T>` or an alias of this
  translation unit for one, is `uninitialized-reference`: a reference is
  bound where it is declared.
- **`out` arguments** initialize only where they are evaluated on every
  path, as an assignment does, in every expression, a returned value
  included; a `throw` ends a path. Within one expression, the initialization analysis
  follows C++17 sequencing: the operands of `<<`, `>>`, `&&` and `||` and
  the elements of a list `(a, b)` are evaluated left to right, an
  assignment's right operand before its left, and an `inspect` subject
  before its alternatives. A read evaluated after an
  `out` argument whenever it is evaluated reads the initialized object, as
  in `std::cout << h(out b) << b;`, `v: std::vector<int> = (init(out e), e);`
  and `v[i] = init(out i);`. Other operands, such as those of `+` and the
  arguments of a call, are unsequenced, so a read beside an `out` argument
  there is a use before initialization. Locals that one expression
  initializes must be initialized in declaration order in this evaluation
  order, taken as left to right where it is unsequenced, so `a = f(out b);`
  initializes `b` first. One object passed as `out` twice in one
  expression, an expression body or a contract included, is
  `out-argument-twice`.
- **Handlers.** A `catch` handler starts from each state in which its `try`
  block may throw. A throw from an expression statement undoes the
  initializations it makes (an `out` argument's object is destroyed), so a
  local that the block's last statement initializes, directly or as an `out`
  argument, may be initialized in a handler:
  `try { n = parse(s); } catch (_) { n = -1; }`.
- **Captures.** A capture `x$` of an uninitialized local is reported at the
  capture.
- **Members in a constructor.** An `operator=: (out this, ...)` checks its
  preconditions, then initializes the data members in declaration order: by
  its leading `member = value;` statements, or by their default
  initializers. A read of a member not yet initialized at that point, `y` or
  `this.y`, in a precondition or in a leading statement, as in
  `x = y; y = 2;`, is `use-before-initialization`; a mention in a
  compile-time context is not a read.
- **`assert<unevaluated>`** conditions are checked for uninitialized reads,
  since they are compiled.

## Safety checks

- **Comparisons.** A single or chained `<`, `<=`, `>` or `>=` goes through
  `cpp2::impl::cmp_*`, which rejects `bool` operands and mixed signedness
  when the Cpp1 is compiled. When both operand types are known, the
  translator reports a mixed-sign comparison itself
  (`mixed-sign-comparison`). An unsuffixed literal is signed, like any other
  operand, so `s > 0` for an unsigned `s` needs `0u`; the message says so.
- **Null pointers.** A pointer initialized or assigned from `nullptr`, an
  integer or `()`, also in grouping parentheses, is rejected
  (`pointer-null-initialization`, `pointer-null-assignment`).
- **Constant expressions.** A bounds-checked subscript works in a constant
  expression: the runtime builds the failure message only on failure.

## Metafunctions

- **Reserved members.** A metafunction reserves exactly the names it
  generates, such as `_value`, `_storage`, `_discriminator` and `@union`'s
  `is_`/`set_` accessors; a member declared with one is
  `metafunction-reserved-name`, naming the metafunction. Other names that
  begin with `_` are free.
- **`@union`.** Two alternatives with the same name are
  `union-duplicate-alternative`, and an alternative named `_`, which its
  accessors cannot name, is `union-anonymous-alternative`. Any Cpp2 type can
  be an alternative, a pointer or function pointer included. A move-only
  alternative keeps the generated
  copy members, since constraining them without types would work only in
  template unions.
- **`@enum`** values start at 0, as metafunctions.md's prose ("one higher
  than the previous enumerator") says; the `skat_game` comment that says 1 is
  a documentation error. An enumerator `_;` is `enum-anonymous-enumerator`,
  since a value is spelled with its name, and two `@enum` or `@flag_enum`
  enumerators with the same name are `enum-duplicate-enumerator`, at the
  second.
- **`@regex`** follows Perl's documented rules and diagnoses what Perl
  rejects. Where Perl's result depends on its optimizer, a group in a loop
  keeps its last successful match, as PCRE and Python do; a result perlre
  does not state follows the rules it does state. `search(str, start)`,
  `match(str, start)` and `find_all(f, str, start)` search `str` from `start`
  as Perl does from pos(), and `find_all` starts each search where the
  previous match ended, as `//g`. UPSTREAM_DIFFERENCES.md lists the cases.

## Mixed files

- **`using` lines.** A `using` line is Cpp2 exactly in the documented forms
  `using a::b;` and `using a::_;`.
- **Byte order mark.** A leading UTF-8 byte order mark is skipped.
- **`#if` branches.** Only the first branch of an `#if` counts Cpp1 braces,
  as if it were taken. Cpp2 declarations inside `#if` branches are
  unconditional.
- **Nested Cpp2.** A Cpp2 declaration nested in a Cpp1 body is left to the
  Cpp1 compiler.
